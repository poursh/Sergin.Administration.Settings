# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Sergin.Administration.Settings is the Settings module (Postgres schema `st`, module name `Settings`, text key segment `settings`, routes under `/st/`, permissions `permission.st.*`) of the **Sergin** platform — a .NET 10 modular monolith whose host repo, **Sergin.MeterMinder**, composes it with **DeviceManagement** and **UserAccess**. It sits beside UserAccess under `src/Modules/Administration/` and shares UserAccess's "Administration" drawer group. It holds the features the platform itself needs and has no business domain: localization first (languages and translations, implementing SharedKernel's `ITranslationStore`), later settings. Operational monitors do not belong here: they go in a future sibling module, `Sergin.Administration.Monitoring`. (It was the Platform module, schema `pf`, until 2026-11-06.) Business features never belong here, and identity and access stay in UserAccess. Design: the host repo's `docs/superpowers/specs/2026-11-05-localization-design.md`, decision 20 onwards.

**This repo is embed-only.** There is no solution file, no `Directory.Build.props`/`Directory.Packages.props`, no dev config here. It only compiles as a git submodule at `src/Modules/Administration/Settings/` inside a host repo (today: [Sergin.MeterMinder](https://github.com/poursh/Sergin.MeterMinder)) that also provides `Sergin.SharedKernel` at `src/SharedKernel/`. `dotnet build`/`dotnet test` run against the *host's* solution; the host's root `CLAUDE.md` holds every cross-module convention (layering, CQRS, validation, aggregate features, Blazor views) and this file only adds what is specific to Settings.

## Current state

Two aggregates, `Language` and `Translation`, with their write slices, reads and admin pages.

- **`Language`** (`Languages/` in every layer, no feature level above it): `Audited().Versioned()`, not soft-deletable, not scoped. `CultureName` (max 20) is normalised by `CultureName.Normalise` to `CultureInfo.GetCultureInfo(value, predefinedOnly: true).Name` (`FA-ir` → `fa-IR`) and refuses an unknown culture, the invariant culture and any English culture (`LanguageErrorKeys`, declared in `LanguageTexts`); `LanguageDisplayName` (max 100); `LanguageDirection` `FromCulture | LeftToRight | RightToLeft` and `LanguageStatus` `Draft | Published`, both stored by name. `IsRightToLeft` is derived (`Language.ResolveRightToLeft`), never stored. `ILanguageRepository` declares `IUniqueKeyRepository<CultureName>`; `IsTakenAsync` compares the normalised culture and `ix_language_culture` is the guarantee (created by the module's `InitialCreate`).
- Slices: `AddLanguage`, `RenameLanguage`, `SetLanguageDirection`, `PublishLanguage`, `UnpublishLanguage`, `DeleteLanguage` (a hard delete; its translations go in the same statement through the cascading FK, and the culture's cache entry is refreshed), `GetLanguageById` (versioned), `GetLanguageList` (`LanguageListFields`: search culture and display name, sort by culture). Every write requires `LanguagePermissions.Manage` (`permission.st.languages.manage`), every read `LanguagePermissions.Read`; every write but Add is version-guarded by its type (`ISetPropertyCommand`/`ITransitionCommand`/`IDeleteCommand` on the versioned `Language`). Each write handler calls `TranslationCacheRefresher.LanguagesChangedAsync` (`.Application/Localizations`) after `SaveChangesAsync`, since the cache loads the language list once; the refresher runs without the caller's token and, if the refresh fails, logs a warning and calls `ITranslationCache.InvalidateLanguages` instead of failing the saved write. The translation handlers call its `TranslationsChangedAsync(culture)`, which refreshes that culture and calls `ITranslationCache.Invalidate(culture)` when the refresh fails. A WebApi endpoint ships per slice.
- **`Translation`** (`Translations/` in every layer): `Audited().Versioned()`, not soft-deletable, not scoped. `LanguageId`, `TranslationKey` (a `TextKey` value as stored, max 300), `TranslationText` (max 4000) and `SourceText` (the catalog default it was translated from, `text`). FK `language_id` → `st.language` with `ON DELETE CASCADE`; unique `ix_translation_language_id_key` (created by `InitialCreate`). There is no navigation between the two aggregates.
- Slices: `AddTranslation(ParentId /* the language */, Key, Text)`, `ChangeTranslation(Id, Text)` (an `ISetPropertyCommand`, version-guarded by its type), `DeleteTranslation(Id)` (versioned; only an **orphan**, a row whose key the catalog no longer declares), `GetTranslationById` (versioned, what Change/Delete are sent at), `GetTranslationList(ParentId /* the language */, Module?, Category?, Status?)` and `GetLanguageProgress(LanguageId)`. Writes require `TranslationPermissions.Edit` (`permission.st.translations.edit`), reads `LanguagePermissions.Read`. Add and Change store `SourceText` = the catalog's current default. Validators (`TranslationRuleBuilderExtensions`): the key is declared (Add; for Change the row's key still is), not yet translated (Add), the text non-empty and ≤ 4000, and **its placeholder set equals the default's** — refused as code `Text` with `settings.translations.errors.placeholders-differ`, `{Expected}` listing the default's placeholders.
- The list is **merged in memory** (`TranslationListMerge`: the catalog's entries × the language's rows read by Dapper) and then filtered (module segment exact, category path or below, status, origin — `TextOrigin.Ui` shown as "Screens", `Application` as "Messages"; an orphan has no origin and matches neither), searched (`Term` over key, default and text, ordinal case-insensitive) and paged by the handler, always ordered by key; `TranslationListFields` declares no sort or filter field. Statuses: `Untranslated` (declared, no row), `Translated`, `NeedsReview` (row's `SourceText` ≠ current default; still served), `Orphaned` (row, no declaration; listed with its stored source as the default, never served). Progress counts Translated + NeedsReview over the catalog's total; orphans count in neither.
- **`SettingsTranslationStore`** (`.Infrastructure/Localizations`) replaces SharedKernel's empty store (`services.Replace` in `LanguageInstallationExtensions`, since `AddSerginCore` registers the default before the module loop). It is a singleton and opens a scope per call for the scoped `IDbConnectionFactory`. `GetLanguagesAsync` reads `st.language`, drafts included, with the **resolved** direction in `LanguageInfo.IsRightToLeft`; `GetTranslationsAsync(culture)` reads that culture's rows of `st.translation` (joined to `st.language`, any status, culture compared without case).

- `SettingsModule` (`Sergin.Administration.Settings`) implements `ISerginWebApiModule` and `ISerginWebUiModule`: `Name` `"Settings"`, `Schema` `SettingsDbContext.Schema` (`st`), the three assembly markers, `UiAssembly` → `SettingsBlazorAssemblyReference.Assembly`; `AddServices`/`MapEndpoints` call `LanguageInstallationExtensions`.
- The module has **no** `<Module>Texts` class in `.Application.Configurations`: the drawer group is SharedKernel's shared Administration group. Its one module-level text is `SettingsUiTexts.MenuTitle` (`settings.menu-title`, "Settings", in the RCL root), the caption `SettingsModule.NavCaption` returns, shown over Languages inside the Administration group. `LanguageTexts` (`settings.languages`, with `.directions`, `.statuses`, `.errors` and `.overview`) and `TranslationTexts` (`settings.translations`, with `.statuses` and `.errors`) declare a `FieldText` per shown command property and list field (`Culture`, `DisplayName`, `Direction`, `Key`, `Text`, …), `Singular` and the error texts. The pages' texts (titles, confirms, statuses, directions, overview figures) are only the UI's, so since 2026-11-07 they are declared in the RCL as `LanguageUiTexts` and `TranslationUiTexts` (`Presentation.Blazor/<Aggregate>/`), on the same categories, so their keys did not change; a new page text goes there. Both feature configurations call `.Texts(...).Named(<Aggregate>Texts.Singular)`, and ids (`Id`, `LanguageId`) are `NotShown(...)`. `CultureName`'s refusals carry keys from `.Domain/Languages/LanguageErrorKeys.cs`, declared in `LanguageTexts`; a handler-raised refusal (`AddTranslation`'s unknown key) names its `TranslationTexts` key directly. The admin pages show the module's own texts translated like any other, and a translation of a Settings key is edited on the same page.
- `SettingsNavigation` (`.Presentation.Blazor`): `Group` is `SerginNavGroups.Administration` (SharedKernel, `Sergin.SharedKernel.Presentation.Blazor.Modules`; the same group UserAccess returns, so the drawer and breadcrumbs read `Home > Administration > Languages`); `Languages` (`/st/languages`, requires `LanguagePermissions.Read`, `Order: 300`, after UserAccess's Users 200 and Scopes 210) is its one entry.
- Pages are **generated** (SharedKernel's generated aggregate views; `LanguageViewConfiguration` and `TranslationViewConfiguration` in the RCL, each aggregate's `Pages/` holding only the thin `@page` + `SerginPageLayout` + generated view). `/st/languages` is the generated list (search by culture and display name, a row Delete); `/st/languages/new` the generated create form; `/st/languages/{Id}` the generated detail: `LanguageProgressSlot` as the overview card (`GetLanguageProgressQueryCommand` is an `IEntityOverviewQuery`), Publish or Unpublish as a reverse pair (`AppliesWhen` on the language's status, so a list row offers neither), a Translations link action (no permission of its own: whoever sees the language holds `languages.read`, which the translations list requires), Delete, Rename as an inline edit (`SerginEditMode.Inline` on a text value: the `GeneratedInlineEditCard` below the fields, a blank value refused by the validator) and SetDirection as an inline select (`LanguageDirectionValue` renders the setting with the resolved direction, "From the culture (Left to right)", for a reader who cannot edit). Status, direction and origin texts are `Values<TEnum>` value texts (`settings.languages.values.language-status.draft`, …) declared in `LanguageTexts`/`TranslationTexts`; the info button reads `GetLanguageAuditQueryCommand`, global since a language has no scope. `/st/languages/{LanguageId}/translations` is the generated list under a parent (`ListUnder<Language>`): the table is replaced by `TranslationGrid` in the `SerginViewSlot.ListBody` slot, which keeps the module, category and status filters feeding the query's own `Module`/`Category`/`Status` properties (Apply copies the pickers into the applied values the load sends), and the inline edit: a row with no translation sends `AddTranslation`; one with a translation loads it versioned when the edit opens and sends `ChangeTranslation` at that version; a refusal is notified as the pipeline returns it, and a stale answer reloads the row's version and says what the translation reads now, keeping the user's text. Only an orphan offers Delete; the edit commands show only to a holder of `TranslationPermissions.Edit`. The header Reload bumps the context's `Generation`, which reloads the grid.
- `SettingsDbContext` (`.Infrastructure.Data`) maps schema `st` with the `AggregateFeatures` override from the start; it does **not** opt into the outbox. The module has exactly one migration, `InitialCreate`, which creates the `st` schema and the `language` and `translation` tables with their audit and row-version columns, the unique indexes and the cascading FK; it is in a file-scoped namespace (converted by hand, as every scaffolded migration must be) and is the host's reference example of that shape. A later schema change adds a migration after it, following the host's pattern: add columns nullable, backfill, then `NOT NULL`, in the same PR as the feature.

## Conventions specific to this module

- On disk the aggregates are still top-level folders in every layer (`Languages/`, `Translations/`). A feature level above the aggregate (`Localization/Languages/...`) is allowed when the module grows — a feature's aggregates are its text categories (`settings.languages.*`, `settings.translations.*`) — but it is not there today.
- Permissions are not scoped and named `permission.st.<resource>.<action>` (`permission.st.languages.read`). `LanguageAggregateFeatureConfiguration` and `TranslationAggregateFeatureConfiguration` register them next to `.Texts(<Aggregate>Texts.Category)`. **Declare `Texts(...)` together with `Permissions(...)`**: a permission's label key follows the root's text category once the root names one (`<category>.permissions.<action>`) and falls back to `<module>.<resource>.permissions.<action>` until it does, so adding `Texts(...)` later moves every label key of the aggregate and orphans their stored translations.
- Every page route starts with `/st/`; the host refuses to start otherwise.
- Composing the module into a host takes **two** `ProjectReference`s — `Sergin.Administration.Settings` and `Sergin.Administration.Settings.Presentation.Blazor` (static web assets do not flow through the plain-SDK composition root) — and one `new SettingsModule()` in the host's modules collection.
